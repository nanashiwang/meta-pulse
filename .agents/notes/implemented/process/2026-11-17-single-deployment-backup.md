# Agent Note: 部署备份收敛为最近一份

Status: implemented

## Problem

生产部署备份累计约 26 GiB，八份中五份为失败更新现场。用户明确要求只保留最近一次备份。仅把成功保留数量从三改为一不能解决失败备份永久累积。

## Decision

复用更新锁、状态文件、预览与安全目录删除，默认保留一份成功更新前备份。在成功更新之后回收更早的已知 failed/running 现场；比最后成功更新更新的失败现场继续保留，直到后续更新成功。未知格式、损坏状态、显式 .keep 和不安全目录仍保护。增加在同一更新锁内执行的 prune 操作，供现有服务器清理而无需重新部署。保留 0 禁用及自定义 N。

构建缓存仍按现有 8 GB 目标、20 GiB 空闲门禁与更新前后维护；当前约 7 GB，无证据要求清空缓存或重启 Docker。

- [缓存预算](../../implemented/process/2026-11-13-build-cache-budget.md)：复用，无行为改变。
- [迁移](../../implemented/process/2026-10-27-metar-server-migration.md)：历史归档不属于本次部署备份目录，不清理。

## Alternatives considered

- 仅设置 --backup-keep 1：实现简单，但五份失败备份仍永久占空间，不能满足需求。
- 按时间保留最新目录并立刻删除其余：数量最少，但最新可能只有部分 dump；选择成功验收后淘汰旧现场，部署中允许暂时多一份。
- 清空构建缓存：能再释放少量空间，但会增加论坛编译耗时；当前容量受控，维持已有预算。

## Verification

`make deploy-test` 通过，13 项保留回归和 7 项构建缓存回归覆盖默认一份、旧失败/中断回收、新失败保护、无成功基线不删、禁用/数量/固定/未知/不安全路径、锁冲突及删除失败。更新链路验证全部验收成功前不淘汰旧恢复点。生产持锁检查最新成功备份的 SQL 完成标记、配置、密钥与附件目录并记录 SHA-256 后，删除七份旧备份；目录从约 26 GiB 降至 3.2 GiB，根盘使用率从 65% 降至 40%，可用约 55 GiB。清理不重启容器。校验值仅证明本次保留材料可读，未执行数据库恢复演练。

## Consequences

成功更新后不再保留较早失败现场，恢复历史窗口缩短；部署进行中及新失败恢复前可暂时多份。备份数量不是硬磁盘配额，未知或显式固定目录仍需单独处理。更新前创建的备份不是持续备份，不代表具备最近业务写入的时间点恢复。
