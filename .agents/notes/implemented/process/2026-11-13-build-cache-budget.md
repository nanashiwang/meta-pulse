# Agent Note: 部署构建缓存预算与磁盘前置检查

Status: implemented

## Problem

2026-11-13 生产 96 GiB 根盘满，Answer MySQL binlog 写入等待使浏览次数更新阻塞，详情接口超过 10 秒超时。Docker 回收可再生成缓存报告 55.63 GB；同期备份约 13 GB，不是同一类数据。生产每五分钟检查 main，有变化才构建；默认 builder 最大缓存约 71.71 GiB，与数据库共盘不合适。

## Decision

复用 update.sh 更新锁和既有轮询，在同提交退出前执行本地默认 Docker builder 缓存维护；保留目标 8 GB，空闲目标 20 GiB。备份后、构建前再次检查空间，更新退出时回收缓存。只使用 Docker 缓存 GC，不删除镜像、卷、数据库日志、上传或备份。不修改 Docker daemon 或新增定时器。缓存目标不是硬配额，在用缓存不可回收；不足空间拒绝更新并保留现有服务。

## Existing capabilities and note audit

备份保留笔记负责成功三份及失败/pin 保护，本篇部分重叠但不改变其规则；版本预检查负责同提交跳过构建，本篇保留该行为，仅增加维护。服务器迁移笔记为历史磁盘事故，不是现有缓存策略 owner。复用现有 Python 与更新锁，不独立实现备份清理。

## Alternatives considered

- 调整 daemon GC：能约束更多构建，但涉及主机全局配置和重启/版本差异；现有更新入口可在线处理，不打断数据库。
- 每次清空缓存：空间最省，但完整编译更慢；保留 8 GB 热缓存折中。
- 只按缓存年龄清理：频繁发版时缓存都很新，首次应急按 24 小时只释放约 204 MB，不足以解决。

## Verification

`make deploy-test` 通过；新增 7 项容量/CLI/失败回归及更新链路断言，覆盖低磁盘阻止构建、清理失败、远端 Docker 拒绝、同提交仍维护及不删除运行数据。生产在更新锁内执行助手成功，三个路径均报告约 52.2 GiB 空闲。此前已验证受影响帖子正文和另帖九个回答恢复，积压事务归零。

## Consequences

默认 builder 的未使用缓存属于主机级共享资源，其他项目重编译可能变慢。无法约束单次构建峰值或人工 Docker 命令；20 GiB 是前置阈值而非空间预留。版本检查仍需网络，维护先于 fetch，网络失败也可回收缓存。
