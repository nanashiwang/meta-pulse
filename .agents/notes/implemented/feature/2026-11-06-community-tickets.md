# Agent Note: 社区互动与签到赠券

Status: implemented

## Problem

用户要求当前抽奖增加社区来源：帖子收到10次评论得1券，每天最多2券；给别人点赞40次或评论20次各得1券，分别累计、合计每天最多3券；签到每天1券。0.2元是消费获券的等价描述，不直接增加余额。原内容不产券约束被本次明确授权的限额赠券例外取代，贡献值仍只认真实付费使用。

## Decision

复用 Answer 签到与内容事实、保护绑定、community-bff、Pulse Ledger/发行批次/现有抽奖。插件独立持久化来源去重、日进度与待交付券，后台有界扫描，服务故障不阻断发帖或签到。按上海自然日分别累计；只认启用后、绑定后的有效互动，排除自评自赞、隐藏删除内容与撤赞，点赞对象与操作者终身去重。评论包含 Answer 回答及评论；收到评论按本人帖子汇总。达到门槛后冻结赠券资格，后续删除不自动追扣，保留来源供人工审计。

首次游标初始化先执行独立只读 SELECT，再写插件游标，避免 MySQL Repeatable Read 下 INSERT SELECT 对 Answer 来源表加共享锁；已有游标不重新扫描。

Pulse 只接受 community-bff 签名的固定类别、日期及日序号，服务端限定2/3/1上限，身份来自签名。稳定赠券编号与首次规则/期限、账本、发行批次、审计同事务；重试不受规则更新影响。独立 ticket_bonus 操作不计贡献、不消耗付费未成券余数，抽奖沿用当前奖池和预算。未绑定仍能签到获得经验，绑定前不补发券。

## Existing decisions

检索签到/评论/点赞/ticket/engagement。[当前规则笔记](../../implemented/feature/2026-10-09-pulse-current-reward-rule.md)和[券重置笔记](../../implemented/process/2026-11-01-ticket-reset.md)部分相关，继续拥有消费、最新奖池和历史数据边界；本次不重写其决定。社区经营只读统计不适合作发券凭据，保留独立。没有现成社区赠券实现。

## Alternatives considered

- 浏览器报告互动次数：改动少，但计数可伪造，不能用于券账本。
- 将社区行为折算成付费贡献：能复用产券路径，但混淆毛利与付费来源，且污染退款和余数。
- 每次访问只查当天数量：简单，但跨午夜或服务故障可能丢奖励，选择持久游标与待交付记录。

## Verification

隔离 MySQL 8.0 验证分项阈值/每日上限、自评/隐藏/删除/撤赞/跨日重赞排除、绑定和上线时间、上海午夜、100 并发来源重放、100 并发 Pulse 交付、规则更新与丢响应恢复、注入 outbox 写失败后事务回滚及游标重试、持久重试调度。赠券能通过现有 v3 Action 正常扣券抽奖并重建账本，付费贡献余数保持不变。CI 复用 MySQL 8.0/8.4 矩阵。

本地全部 Go 测试、make test、vet、Pulse/博客/正式前端构建通过。实际浏览器以本地合成数据验证签到请求不携带身份或金额、进度与券余额刷新、中英文和320px深色布局、503及恢复；不代表生产实际领取。截图位于 output/playwright/community-tickets-*.png。发布与部署分开核实。

## Consequences

源内容删除在首次扫描前不计入，不能保证奖励短暂存在的违规内容。后台有延迟，需显式展示等待同步；采集与发券失败分别重试。多表与持久来源随 Answer 完整备份，不能单独回退到不认识 ticket_bonus 的 Pulse 版本。
