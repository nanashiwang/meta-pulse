# Agent Note: 未用券统一使用最新抽奖规则

Status: implemented

## Problem

用户明确要求管理员保存新规则后，所有未用券统一使用最新奖项、概率与预算，并明确保留每张券原来的有效期。v0.2.37 的规则组选择和同批五连抽增加了日常使用门槛。

## Decision

复用不可变规则快照，区分发券归属与执行抽奖规则。券的账户、发放记录、有效期及消费分配仍归原来源；新 Grant、概率、HMAC 版本、预算与结算归最新启用规则。发布新版配置与首次 Action 通过同一个规则创建锁串行化，锁后使用当前读确认最新版本；已经提交的 v1/v2/v3 结果和拒绝回执优先恢复。

v3 预览统一返回券余额、最新奖项和最多五次抽取的签名选择。后台优先额度资格有效的券，再按原获得时间选取；每次选择绑定最新规则、原发券归属、批次和资格。五连抽可以跨批次，每个操作保存自己的选择，规则切换或资格变化要求重新确认。页面显示单次及五次适用范围；到期券使用最新 EXP 子奖项，原有效期不刷新。旧版未提交请求要求升级确认，已提交请求不重新解释。

## Existing capabilities and note review

复用 `/pulse`、规则查询、Action、BFF、管理配置、双幂等回执、Ledger 与 Outbox；没有新增发券系统。原[规则组笔记](../../implemented/feature/2026-10-08-pulse-ticket-selection.md)的展示及规则归属决定被本方案取代，拒绝提交与恢复机制继续复用，因此保留并互链。动画和加载壳笔记与本次无决策重叠。

## Alternatives considered

- 修改旧规则、批次或迁移券余额到新账户：查询容易，但会破坏历史规则和账本来源，且改变贡献余量重建，拒绝。
- 继续让用户选择历史规则组：兼容旧权益，但与用户最新明确要求不符。
- 请求完全不携带版本和选择：请求简单，却会在网络重试或配置变化后换概率；采用版本化签名预览，改变后重新确认。

## Related decisions

[50% 额度概率预设](2026-10-09-pulse-fifty-percent-preset.md)沿用本篇规则归属与恢复机制，仅扩展管理员可加载奖项和用户概率展示。

## Consequences

所有未用券立即采用最新奖项及预算，期限保留，用户无需理解来源批次。原 Grant 与其预算仍负责历史预留、结算、撤销；不将新旧预算相加。规则创建与首次 Action 共用事务锁，增加全站新抽奖的串行临界区；原当前奖池预算本身也有行锁，未来扩展吞吐需同时验证这两层锁序。

前端 v3 允许各次选择不同但保留原协议和原请求；历史 v1/v2 只能恢复已提交结果。整体升级 API/BFF/前端并排空旧写请求，回退前关闭 Action 入口。此次不改具体预算数值、不增加每日券、不部署生产。

## Verification

- `make test`、`make vet build deploy-config-test` 通过，包含前端、BFF、旧协议恢复与请求指纹检查。
- 隔离 MySQL 8.0 的 `make test-integration`（含 race）通过：旧预算耗尽仍能使用新规则、跨来源五次选择、最新奖项/预算、原 30 天期限不被新 60 天设置延长、账户由账本重建、持久拒绝/提交回滚、同请求 100 次恢复、最后一张并发竞争以及等待期间跨期限。
- 使用真实 MySQL 事务人为停在规则锁之前，先发布新规则，证明此前已建立 Repeatable Read 快照的在途请求仍读取最新规则并拒绝旧预览。
- 本地生产构建浏览器验收通过：五次选择跨来源，第三次响应丢失后刷新只查询、继续仍总计五个原操作；规则更新拒绝旧预览；390px 暗色与 320px 英文无横向溢出，混合期限五连抽分别展示两类概率，未绑定账号不显示抽奖入口，管理员确认文案明确全部未用券及原期限。截图位于 `output/playwright/current-rule-*.png`。
- 本地受控响应不代表生产普通账号或真实到账验收；Release 与附件另行核验，未部署生产。
