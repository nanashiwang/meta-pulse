# Agent Note: 用户统计全局排序与奖励汇总

Status: implemented

## Problem

历史累计发券含已清零券，名称容易误解为可用总量；用户需要消费券及到账奖励，并按全部筛选结果排序。原生列表先分页、插件只补本页统计，直接排序当前页不满足要求。

## Decision

沿用 Answer 管理员列表筛选和插件最多 100 人的统计接口。显式选择排序时，浏览器按 100 人分批加载当前筛选结果及统计，完整成功后排序再分页；失败拒绝展示部分排名，切换筛选/离开页面取消旧请求。整数比较避免浮点精度丢失，缺失统计置末尾，同值用用户 ID 稳定排序。默认不排序仍使用原生分页。显示历史累计获券并说明含清零历史，不改账本；消费只计 ticket_spend，到账奖励只计 settled 且未撤销的抽奖 Grant，额度与经验分开。现有统计笔记的批量和事实源边界继续适用，当前页限制仅对默认模式适用。

## Alternatives considered

- 仅排当前页实现简单，但不满足用户明确要求。
- 新建跨服务物化排名可以降低大规模排序成本，但需要额外同步、更新时序与恢复契约；当前管理员手动查询复用现有接口，暂不引入新事实副本。

## Testing

MySQL 8.0 / 8.4 隔离数据库回归通过：累计 258912、清零 258911、消费 1、剩余 0，待发/失败/撤销/非抽奖奖励不计到账。HTTP 契约与插件投影测试、社区前端测试、Answer 补丁应用、TypeScript、ESLint 和 Answer UI 正式构建通过。

Chromium 组件夹具使用真实修改后的 Users 组件、React/Bootstrap/路由，模拟管理接口及外围组件；150 用户覆盖跨页排名、同值稳定排序、翻页、奖励显示、列偏好、接口失败不显示部分排名、重试与原生筛选。不是生产登录或完整后台端到端验收。

生产只读核对：API 用户 278 历史累计 258912，旧铸券 258911 被 2026-11-01 的 ticket_adjustment 全量清零，之后 ticket_bonus 1、ticket_spend -1，净余额 0。本次不改写该历史或操作运营数据。

## Consequences

全局排序的请求量随筛选人数增长，浏览器仅保留当前管理员页面的数据；提供加载和错误反馈，不截断结果冒充全局。生产不自动修改运营数据。
