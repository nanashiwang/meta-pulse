# Agent Note: 抽奖结果自动恢复与到账查询解耦

Status: implemented

## Problem

用户要求中奖结果即时展示，到账延迟不能阻断下一轮。2026-10-09 17:55 的网关只读日志显示三个 Action 返回 201、第四个返回 503；截图停在 3/5。现有服务已异步交付奖励，但浏览器遇到一次不确定响应便退出连抽，且完成后完整页面刷新把规则查询与历史读取一起等待。

## Decision

复用普通 Action、稳定操作编号、服务端 Grant 和后台 Outbox，不增加资金事务或更换随机结果。在用户本次主动发起/继续的操作中，临时错误最多自动恢复两次：退避后先查询原 Action，找到即直接使用；查询成功且未找到时才用原编号和原选择重试。明确拒绝、身份错误、冲突立即停止；查询失败不能视作未执行，切页/身份变化停止未发请求。刷新仍只读恢复，持续故障保留原请求并显示“继续完成本轮抽奖”。

结果确认后清除操作日志与到账状态无关；单独刷新最新规则来开放下一次抽奖，历史/到账读取随后独立进行。历史读取失败保留原内容并提示，不禁用抽奖、不声称到账。

## Existing capabilities and note review

复用 `/pulse`、PulseDrawSession、现有后台发奖与到账轮询；API/BFF 已有异步交付回归。[当前规则笔记](../feature/2026-10-09-pulse-current-reward-rule.md)部分重叠，保留签名选择与明确拒绝规则；[紧凑历史笔记](../simplification/2026-10-09-pulse-compact-history.md)部分重叠，保留折叠状态；[动画笔记](2026-09-29-pulse-skip-charge-retain-reveal.md)无决策冲突，不改演出时长。旧规则组笔记的拒绝与历史恢复继续由当前规则笔记承接，不另改契约。无需新接口、数据库或权限。

## Alternatives considered

- 服务端原子五连抽：可避免五个网络往返，但需要新的批量预算、拒绝回执与历史协议。当前故障为单次 503，复用已存在的幂等恢复可以直接消除短暂失败造成的手动中断，不扩大资金契约。
- 出错即清除原操作并开放新抽奖：交互简单，但不确定响应可能已经扣券，丢失原结果恢复入口，拒绝。
- 等全部奖励到账才解除忙碌：能保证显示最终到账，但把下游故障传递到抽奖体验，违背用户要求与原异步设计。

## Verification

会话回归验证丢响应后查询原结果自动完成五次，提交前 503 查询未找到后仅重发原编号；持续错误最多三个 POST，拒绝/冲突不重试，异常查询不重发，切页不追加扣券，刷新仅查询。壳层回归验证全部 pending 时可再次完成五连抽，双语提示随切换更新。

正式前端测试、博客/社区构建与既有 BFF 异步交付测试通过。本地生产壳与合成 API 验证：第四次返回 503 后共六个 POST、五个唯一 Grant，只扣五张；历史读取延迟 30 秒时两轮可连续揭晓，十个 Grant 全部 pending；历史 503 不锁按钮、恢复后卡片与展开记录更新 settled；资格读取失败仍锁按钮且错误提示不被历史刷新覆盖；持续 503 三次后保留原操作，手动继续完成原五次。桌面浅色与 390px 深色下检查结果和恢复按钮。截图保存在 `output/playwright/pulse-recovery-*.png`，不代表生产真实奖励测试。

## Consequences

短暂故障增加有限的查询与退避延迟。持续服务故障或最新资格不可核验时仍必须停止，不能为视觉完整而虚构中奖结果。浏览器与本地模拟验收不代替生产真实发奖；本次不部署生产。
