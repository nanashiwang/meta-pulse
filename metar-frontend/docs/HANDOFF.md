# METAR 新前端 · 开发交接说明

版本 1.1.0 · 2026-09-07

## v1.1 展示层修订

当前用户要求以正式平台的内容布局展示，而不是展示产品介绍或原型说明。默认入口为 `index.html`：删去新手引导、Pulse 宣传、推荐讨论、安全提示等右侧附加卡片、首页欢迎横幅与左栏宣传块；Pulse 保留普通导航入口。已删除的侧栏不保留栅格占位，主区最大宽度为 1120px，精选卡片顶部、底部及问答列表边缘统一对齐。手机底部导航不再给演示栏预留空隙，并保留安全区域适配。

开发入口为 `preview.html`，保留身份、状态、页面地图与重置工具。两者均是同一份本地交互实现，展示界面移除介绍文案不意味着真实认证、发帖或权益到账已经接通。正式构建必须移除模拟状态、身份切换与虚构内容。

保留业务必要的绑定限制、表单校验、权限提示、异常状态、规则与隐私页面；这些不是宣传说明。首页配置 `heroTitle` 现在渲染简短栏目标题，`heroText` 不再显示。

## 1. 这版前端要解决什么

不是再做一个“充值 / 模型列表 / API Key”的控制台，也不是把 Pulse 做成抽奖首页。

首页应回答三个问题：这里的人在讨论什么、有哪些经验值得看、我下一步可以参与什么。读者可以从内容进入讨论，从讨论进入个人空间；需要 API 使用权益的人，再自主完成账号绑定。

建议对外信息层级：

1. **社区**：发现、问答、话题与作品交流。
2. **知识库**：教程、实战、评测方法、复盘与社区指南。
3. **Pulse**：真实 API 使用之后的贡献、券、等级、回馈与结算状态。
4. **开发者入口**：接入指南、控制台、支持与状态。

没有加入现金提现、充值买券、签到生券、论坛互动刷贡献、付费解锁管理权限等越界功能。

这不是线上缺陷扫描报告。由于当前环境无法打开 `metar.uk`，不能断言每一个新增入口在生产站原本不存在。这些是依据项目定位补齐的目标体验，不是对线上已实现情况的虚构结论。

## 2. 视觉与布局

采用低噪声的浅色阅读底，搭配深森林绿与浅绿强调色。社区主要区域重视阅读；Pulse 使用更深的面板形成明确的功能区分，但不抢占首页主叙事。

| 设计要素 | 原型取值 |
|---|---|
| 页面背景 | `#F6F7F5` |
| 卡片 / 顶栏 | `#FFFFFF` |
| 主文字 | `#202A26` |
| 次要文字 | `#788079` |
| 主操作色 | `#1D6549` |
| Pulse 深色面板 | `#203D32` |
| 强调色 | `#C4EEAA` |
| 边框 | `#E5E9E3` |
| 卡片圆角 | 12px |
| 桌面顶栏 / 侧栏 | 72px / 214px |
| 页面最大内容宽度 | 1250px |

字体使用系统字体栈，不分发字体文件。图标为内联 SVG，不需要外部图标脚本。深色模式由 CSS 变量覆盖。

移动端收起桌面侧栏，提供菜单抽屉、底部主导航与紧凑搜索；数据表在卡片内部横向滚动，不把整张页面撑宽。主操作尽量不与标题争抢同一行。

## 3. 页面与入口

完整清单见 `route-manifest.json`。以下是核心模块的适配归属，而非宣称这些精确生产 URL 已存在。

| 原型入口 | 页面职责 | 生产归属 / 适配方式 |
|---|---|---|
| `#/discover` | 发现首页、精选内容、问答流 | 社区展示；需评估 Answer 可支持的主题 / 插件范围 |
| `#/questions`、`#/question/:id` | 问答列表、详情、回答、收藏、举报 | Answer 内容与权限 |
| `#/topics`、`#/topic/:id` | 话题列表、关注、相关讨论 | 优先映射 Answer 标签 / 内容能力；不足项另行确认 |
| `#/knowledge`、`#/article/:slug` | 知识库列表、长文、相关文章 | VitePress；生产继续保留 `/blog/` 基址 |
| `#/publish` | 提问、分享、长文投稿 | 社区内容走 Answer；长文投稿送编辑流程，不直写 VitePress |
| `#/search` | 本地示例搜索 | 生产社区搜索与知识库搜索需明确索引来源、权限和更新策略 |
| `#/login`、`#/register` | 独立社区登录与注册 | Answer；本地注册目标维持 `/users/register` |
| `#/forgot`、`#/verify-email` | 找回与验证流程 | Answer 邮件 / 验证逻辑，前端只呈现实际结果 |
| `#/me`、`#/profile/:name` | 个人 / 成员主页 | 生产应用稳定用户 ID，不以可修改昵称作为身份 |
| `#/settings/*` | 资料、绑定、通知、安全 | Answer 资料与会话；绑定按现有可信链路 |
| `#/pulse`、`#/pulse/rewards` | 权益总览、开启与状态查询 | 生产优先置于现有 new-api 会话 / Signed BFF 后面 |
| `#/pulse/rules` | 规则说明与周期版本 | 静态说明 + 服务端权威规则版本；不由页面决定经济参数 |
| `#/developers`、`#/api-hub` | 对外服务入口与缺失配置提示 | 公开 HTTPS 地址配置，按服务归属跳转 |
| `#/support` | 演示反馈与追踪 | 正式支持系统 / 明确的后端工单能力，尚待适配 |
| `#/status` | 组件状态与来源 | 需接入实际状态源；未配置为未知，不展示虚假正常 |
| `#/admin/*` | 运营布局与操作状态 | 概念工作台。生产社区治理与 Pulse 运维分别授权，不统一假定一个前端角色可操作所有服务 |

**Hash 路由只用于离线原型。** 生产社区与博客的可索引 URL、Canonical、站点地图及内容元数据，应沿用各自正式系统的路由与渲染机制，不以此 HTML 代替 SEO 实现。

## 4. 不要因为统一了前端，就混淆系统边界

仓库当前明确：

- Answer 是社区身份、密码、会话、资料、封禁、内容事实源。
- new-api 是 API 身份、调用、计费、充值、余额事实源。
- Pulse 是贡献、券、奖励、预算、周期与结算事实源。
- VitePress 负责博客 / 长文与搜索引流。
- 社区网关不代理 new-api 或 Pulse。
- Answer 不默认 Fork，不把上游源码纳入本仓库。

因此，**不能直接把这个 HTML 当作“新的 Answer 前端”覆盖上线，也不能照抄 `#/pulse` 为社区同源生产路由并直连 Pulse。**

建议先完成两项适配判断：

**A. 界面适配。** 评估现有 Answer 主题、配置与插件能够覆盖哪些布局。若完全重做问答信息架构需要新的独立前端、上游改动或 Fork，应先提交架构决策与维护成本评估，不把它隐含在一次皮肤改造里。

**B. 跨服务路径。** 社区端可以保留 Pulse 介绍、绑定状态、只读徽章和安全跳转；正式开启 / 回馈操作优先在现有 new-api 控制台内承载，以其会话经 Signed BFF 访问 Pulse。若产品坚持在社区域名承载完整权益操作，必须先批准 BFF、身份派生、网关与跨域方案，并同步更新架构文档。原型没有授权这一变更。

统一的是品牌和体验，不是 Cookie、数据库权限与服务间信任。

## 5. 五条关键流程

### 5.1 新用户与内容参与

访客 → Answer 本地注册 → 邮箱验证 → 可跳过的话题引导 → 浏览 / 提问 / 回答 / 收藏。

不把 API 登录做成社区唯一登录入口。不要求未绑定用户付费。不按相同邮箱静默合并身份。

原型“演示登录”和 `preview.html` 中的底部角色选择器都不是生产认证。所有相关开关必须从生产构建中移除。

### 5.2 可选账号绑定

社区账号 → 说明一对一约束 → 显式确认 → Answer Connector 创建 flow → new-api 同源 bootstrap → 已有 SSO 链路 → 固定 callback → 服务端确认绑定。

本次读取的仓库文档中，相关路径包括：

```text
/answer/api/v1/connector/login/pulse_user_center
/api/forum/sso/bootstrap
/api/forum/sso/start
/api/user-center/login/callback
```

这些路径属于已有链路说明，不是让浏览器把任意参数拼进去调用。应由当前插件与网关控制。

浏览器不能声明可信 `user_id`；不能直接输入 ID 完成绑定；不能依据邮箱进行身份转移；不提供普通自助解绑或换绑。冲突状态必须明确拒绝，并引导原账号登录或支持核查。

### 5.3 内容发布与审核

编辑 → 草稿 → 提交 → 待审核 → 社区发布，或知识库投稿送编辑处理。

正式内容可见性由 Answer 决定。未通过审核的内容不进入访客公共列表。长文投稿通过审核，也不应被前端当作已经发布到 VitePress。

原型用本地状态演示了发布和审核，但没有实现多用户、跨设备协作草稿或正式编辑系统。

### 5.4 Pulse 开启与到账

服务端权益快照 → 用户确认消耗 1 张券 → 一个稳定动作标识 → 权威开启结果 → 待发放 / 已到账 / 撤销或待对账。

关键约束：

- 贡献、券和金额来自服务端，不相信浏览器计算值。
- 新开启使用新的动作 ID；原响应丢失时复用原 ID 查询 / 恢复。
- `pending` 不等于失败，不能换 `source_ref` 重发。
- “刷新状态”只查询原结果，不再次开启。
- 只有服务端确认后，界面才能显示已到账。
- 预算不足、周期关闭、资格不符、券不足与服务不可用要显示不同状态，不统一显示“网络错误”。

原型用固定 `20 cents` 展示一次开启结果，不做随机抽奖。该值、币种、等级、计数和周期号都是示例，不是上线参数。最终展示单位与金额换算必须依据 new-api / Pulse 的实际权威字段确认。

### 5.5 内容奖励

公开内容元数据 → 身份映射与绑定先后校验 → 合格真实付费门槛 → 人工审核 → 独立内容预算 → Reward Grant / Outbox → new-api Benefit。

未绑定、绑定前或绑定同秒的内容不追溯补奖。正文发布、内容审核、奖励候选和资金发放是不同状态。不能因为前端显示“资格通过”而跳过后端校验。

原型内容奖励审批不增加贡献值或券。撤销示例保留原金额，另存对原 Grant 的反向记录；真实撤销应走现有受审计的服务端流程。

## 6. 前端适配层建议

以下是**建议的前端接口抽象名称，不是声称仓库已有的 HTTP 端点**。

```text
CommunityAdapter
  getSession / login / register / verifyEmail / requestPasswordReset
  listQuestions / getQuestion / submitQuestion / submitAnswer
  vote / bookmark / followTopic / reportContent
  getProfile / updateProfile / getNotifications

ContentAdapter
  listArticles / getArticle / submitEditorialCandidate
  searchCommunity / searchKnowledge

BindingAdapter
  getBindingState / beginTrustedBinding / readCallbackOutcome

PulseAdapter
  getUserSnapshot / getPeriodRules / openAction
  getActionByStableId / listRewardGrants / getRewardGrant

OperationsAdapter
  getPublicSiteConfig / updatePublicSiteConfig
  listContentQueue / moderateContent
  listEligibleRewardCandidates / reviewCandidate
  createNextPeriodDraft / readAudit / createSupportTicket
```

正式请求统一返回可呈现状态：成功数据、未登录、无权限、未绑定、绑定冲突、数据未知、处理中、限流、暂不可用及失败恢复指引。具体枚举要与现有后端状态机对齐，不能自行创造与服务端冲突的含义。

前端可以负责展示单位格式化，但不能决定预算、等级、奖励概率、资格或最终入账。不要把 `src/app.js` 中的 mock 数据操作直接替换成浏览器访问内部签名接口。

## 7. 导航与入口配置

已经实现本地可操作的展示配置：入口名称、目标逻辑路由、显示开关、排序、站名、简短首页标题、4 个公开外部服务地址，以及 JSON 导出。

外部入口默认未配置：

```text
consoleUrl   元衡 API 控制台
pulseUrl     new-api 内正式 Pulse 操作页
docsUrl      正式 API 接入文档
statusUrl    实际服务状态页
```

未配置时展示说明和配置入口，不跳向臆造地址。已配置时，用户先确认域名，再以 `noopener noreferrer` 打开新页。原型仅接受无用户名、密码、查询参数和片段的 HTTPS 地址。

生产可进一步把合法地址收敛到显式域名白名单。不要在这里存储 SSO secret、API Key、Cookie、数据库连接串或一次性回调 URL。服务端秘钥必须由独立配置管理。

导航开关只决定展示，不替代权限控制；通过直接 URL 访问时仍需服务端校验。

## 8. 状态与可用性

| 状态 | 用户看到什么 | 用户能做什么 |
|---|---|---|
| 访客 | 公共社区内容 | 浏览、搜索；需要参与时独立登录 |
| 未绑定会员 | 完整社区功能 + 可选绑定说明 | 发帖 / 回答 / 收藏；自主选择绑定 |
| 已绑定会员 | 本人权益快照 | 在服务健康且资格满足时开启 / 查询 |
| 管理员 | 受保护运营入口 | 仅按服务器授予的范围操作 |
| 加载 | 骨架与明确状态 | 保留导航，不编造成功数字 |
| 空内容 | 说明 + 下一步 | 调整筛选、发起问题或返回首页 |
| Pulse 降级 | 不展示过期权益、禁用开启 | 社区继续浏览 / 登录，原操作待查询 |
| 绑定冲突 | 明确拒绝，不覆盖已有关系 | 原账号登录或联系支持 |
| 入口未配置 | 配置缺失说明 | 返回社区或由管理员配置 |
| 发放中 | 原 Grant 记录与查询入口 | 查询原结果，不重复开启 |

原型状态切换是人工演示，不是故障探测。正式状态页必须展示来源与更新时间，失联不能被标成正常。

## 9. 上线适配优先级

**P0：让用户走得通。** 统一品牌导航、保留独立注册与密码找回、问答列表 / 详情 / 编辑器、个人资料、账号绑定说明与冲突、知识库入口、未配置与错误状态。优先保证公开内容可阅读、访客能加入、会员能参与。

**P1：让权益看得懂。** 在现有身份和 BFF 边界内适配 Pulse 页面、规则版本、开启动作确认、原结果查询、回馈列表与降级。补齐内容奖励审核，不混入社区贡献体系。

**P2：让运营接得住。** 公开入口配置、审核队列、支持工单、审计与状态来源。确保每个运营动作都有服务端授权、明确后果与回读验证。

本说明不承诺开发工期；特别是 Answer 布局覆盖范围、跨系统搜索和统一运营工作台，必须先完成适配可行性评估。

## 10. 上线前必须补验

- 真实 Answer 独立注册、密码、邮件验证、封禁与资料维护。
- 真实一对一绑定、跨站 Cookie、flow / nonce、防重放与冲突处理。
- VitePress 基址、文章链接、真实种子内容、索引与 SEO。
- Pulse 实际字段、精度、单位、当前规则和状态枚举。
- 正式动作幂等、超时恢复、查询 / 对账和 new-api Benefit 到账。
- 内容候选资格、绑定时间、独立预算、审核和撤销链路。
- 生产 RBAC、CSRF / XSS 防护、输入验证、服务端审计。
- 真实外部入口、监控来源、时间戳与未知状态。
- 不同浏览器、实际移动设备与完整无障碍检查。
- 生产构建完全移除角色切换器、模拟数据、固定金额、本地假登录和演示审核按钮。

本原型通过的是页面与本地交互测试，不是上述安全、财务或生产集成验收。
