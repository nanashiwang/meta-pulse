# METAR 前端生产化改造方案

> 本文以 `metar-frontend/` 提供的 1.1.0 原型为产品、视觉和路由基线；原型中的本地 mock、演示身份和虚构数据不进入生产。
>
> 更新日期：2026-09-07

## 1. 当前判断

当前线上项目不是“前端功能少一点”，而是**产品层和服务层没有形成完整闭环**：

- 根路径仍由 Apache Answer 默认页面承载，没有 METAR 统一壳层、主导航、侧栏、个人空间和移动端体验；
- Answer 本地注册、登录、问答和资料能力存在，但没有按原型重新组织成“发现 → 内容 → 个人空间”的产品路径；
- Pulse 业务内核已经有账本、券、周期、奖励和幂等规则，但用户端接口仍是内网 Signed API，浏览器不能安全直接使用；
- 绑定入口已经有安全 Connector，但缺少前端的状态页、冲突解释、绑定后权益入口和失败恢复提示；
- `/blog/` 已有独立知识库，但还没有和社区发现、搜索、收藏、投稿路径统一；
- 运营、内容审核、支持工单、入口配置和审计尚未形成正式工作台；
- 邮箱激活依赖 Answer SMTP，当前生产没有 SMTP 配置，因此“用户未激活”是服务配置缺口，不是前端问题。

## 2. 原型可复用范围

可以直接复用：

- METAR 品牌、森林绿视觉变量、浅色阅读底和 Pulse 深色面板；
- 顶栏、桌面侧栏、移动抽屉、底部导航、卡片、表单、状态提示和可访问性规范；
- 43 个路由入口的产品分组和页面职责；
- 访客、未绑定、已绑定、管理员、加载、空数据、降级、冲突、处理中等状态设计；
- 账号绑定的“一对一、不可静默换绑、不能用浏览器声明 user_id”文案和交互。

不能直接复用到生产：

- `localStorage` 中的身份、余额、券、奖励和管理员角色；
- 固定示例金额、固定等级、假登录、假邮件、假审核和本地工单；
- 浏览器直接决定 Pulse 资格、概率、预算、入账结果；
- 把原型的 hash 路由或演示工具栏当成正式后端路由。

## 3. 目标拓扑

```text
浏览器
  │
  ├─ /                         METAR 静态壳层（新前端）
  ├─ /answer/api/v1/*          Apache Answer 社区 API
  ├─ /metar/api/*               社区认证 BFF（由 Answer 插件提供）
  ├─ /blog/*                   VitePress 知识库
  └─ /api/user-center/*         固定绑定 callback / Connector 兼容入口

社区 BFF
  ├─ 从 Answer 已认证会话派生本地 user_id
  ├─ 从受保护绑定关系派生 new-api user_id
  ├─ 使用独立 community-bff 密钥调用 Pulse 内网 API
  └─ 不接受浏览器提交的 user_id、role、签名或预算字段

Pulse 原始 API
  └─ 继续保持内网，不向浏览器、Answer 或公网直接暴露

new-api
  └─ 继续作为 API 身份、模型调用、计费和资金事实源；只保留现有 SSO/Benefit/BFF 边界
```

说明：现有架构文档把浏览器 Pulse 链路写成 new-api Signed BFF。由于当前需求要求尽量不修改 new-api，本方案增加**受 Answer 会话保护的社区 BFF**作为社区入口；它只允许已完成一对一绑定的用户访问本人 Pulse 投影，并使用独立密钥和独立角色。此边界变更在实现 BFF 前必须同步 `docs/ARCHITECTURE.md`、`AGENTS.md` 和测试。

## 4. 路由落地分组

| 原型分组 | 生产事实源 | 第一阶段做法 |
|---|---|---|
| 发现、问题、回答、话题 | Answer | METAR 壳层 + Answer API 适配，不复制内容到 Pulse |
| 知识库、文章 | VitePress | 保留 `/blog/`，先做统一入口和文章卡片，再做跨内容搜索 |
| 登录、注册、找回、邮箱验证 | Answer | 真实调用 Answer，不能继续使用原型本地状态 |
| 个人主页、收藏、草稿、通知 | Answer | 映射 Answer 现有 API，缺能力时显示明确不可用状态 |
| 账号绑定、绑定冲突 | Answer + new-api SSO | 复用现有 Connector；绑定状态由服务端读取 |
| Pulse 总览、规则、回馈 | Pulse | 新增社区 BFF；所有数值、资格和结果服务端权威 |
| 开发者入口、状态、支持 | 配置/运营服务 | 先做只读配置和状态来源，未配置时不跳臆造地址 |
| 内容审核、内容奖励、审计 | Answer/Pulse/运营服务 | 独立权限、独立审计，不混入普通论坛权限 |

## 5. 分阶段实施

### F0：前端生产边界 ✅

- [x] 将 `metar-frontend/` 作为设计源和离线原型保留；
- [x] 新增 `metar-frontend/production/`，生产 Adapter 与原型脚本完全分离；
- [x] 增加 runtime config，外部入口只允许同源路径或无凭据 HTTPS 地址；
- [x] 增加构建门禁：生产产物禁止 mock 数据、演示身份、Pulse 身份头和本地业务账；
- [x] 增加 Python 构建测试、Node Adapter 对抗测试和部署静态检查。

**出口标准**：前端可以独立构建；生产与 preview 明确分离；没有任何浏览器代码可以伪造 Pulse 身份或结果。

### F1：METAR 社区壳层 + Answer 适配 ✅（首轮）

- [x] 新增正式静态前端构建，并由 Nginx 精确匹配 `/` 托管；
- [x] 保留 `/answer/api/*`、`/questions`、`/users/*`、Connector、callback 与 `/blog/`；
- [x] 接通真实发现、问题列表/详情/回答、话题、搜索和知识库入口；
- [x] 登录、注册、找回、发布和写操作继续进入 Answer 原生安全流程；
- [x] 访客可浏览，个人资料、收藏、通知和绑定状态只在真实登录后读取；
- [x] 修正 Answer 找回入口、未激活账号操作拦截、收藏时间字段与通知对象跳转；
- [x] 首页 CSP 禁止内联样式，稳定资源更新时强制重新验证；
- [ ] 后续在不复制 Answer 权限逻辑的前提下，继续统一原生写页面视觉。

**出口标准**：公共内容可读、登录/注册可用、问题详情和发布入口不走 mock。

### F2：账号空间和安全绑定 🟡

- [x] 实现个人主页、资料、收藏和通知的 Answer 只读适配；资料修改与写操作进入 Answer 原生页面；
- [x] 实现未登录、未激活、未绑定、已绑定与暂不可用状态；冲突/处理中待真实回调状态补充；
- [x] 绑定按钮只跳现有 Connector，不接受 user_id、邮箱或 API Key 输入；
- 修复并配置 Answer SMTP，确保激活/绑定邮件真实可达；
- 保留本地封禁、密码、资料和治理角色由 Answer 管理。

**出口标准**：独立社区账号完整可用，绑定成功/冲突/失败都可恢复，重放不会重复绑定。

### F3：Pulse 社区 BFF 与用户权益页

- Pulse 增加独立 `community-bff` 角色和密钥，不复用 `new-api`、`forum`、`admin` 或 settlement 密钥；
- Answer 插件增加认证用户路由，从 Answer session 和受保护绑定关系派生身份；
- 提供只读 summary、period、reward history、grant query；
- 提供带 `Idempotency-Key` 的开启动作，超时只显示“查询原记录”，不得重新随机；
- 前端接通 Pulse 总览、规则、回馈、降级和恢复提示。

**出口标准**：浏览器永远不直连 Pulse 原始 API；同一动作重放 100 次仍只有一个结果；Pulse 不可用时社区正常。

### F4：知识库、搜索和开发者入口

- VitePress 输出文章索引 JSON；
- Answer 问题和 VitePress 文章建立统一搜索适配层；
- 开发者入口、控制台、API 文档、服务状态均使用显式 HTTPS 白名单；
- 未配置地址只显示配置缺失，不跳转猜测路径。

**出口标准**：搜索结果能标明来源和更新时间，外部入口不会携带社区凭据。

### F5：运营工作台

- 站点导航/品牌配置；
- 内容审核与投稿编辑队列；
- 内容奖励候选、审核、独立预算和撤销；
- Pulse 周期、预算、结算、冲突、对账和指标；
- 支持工单、成员权限和操作审计；
- Answer 治理权限与 Pulse 运营权限分离。

**出口标准**：所有写操作都有服务端授权、幂等键、原因和审计；Active Period 核心经济规则不可原地修改。

## 6. 本轮不做的危险捷径

- 不把 `metar-frontend/index.html` 直接复制到 Nginx 作为生产站点；
- 不在浏览器保存或提交 new-api Cookie、API Key、密码、Pulse 签名密钥；
- 不让前端传 `user_id` 决定本人权益；
- 不让社区 BFF 直接写 new-api 余额；
- 不让论坛点赞、回答、签到自动生成贡献值或券；
- 不把内容奖励混入普通贡献值账本；
- 不为了页面好看而隐藏“未激活、未绑定、服务降级、发放中、冲突”等真实状态。

## 7. 验收顺序

1. 先跑原型构建和页面回归，确保视觉基线没有漂移；
2. 再跑 Answer API/Connector/邮箱验证真实链路；
3. 再跑社区 BFF 的身份、权限、签名、幂等和降级测试；
4. 最后做 Pulse 真实 MySQL、预算、结算和线上浏览器验收；
5. 每个阶段完成后中文提交，并只推送已验证的阶段性改动。
